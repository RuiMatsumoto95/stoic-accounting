## 1. 変更の要約

- `fiscal_periods.closed_at`（NULL＝未確定）、履歴表 `fiscal_period_close_logs`（INSERT/SELECT のみ）。
- RPC: `get_period_close_check` / `close_fiscal_period` / `reopen_fiscal_period`。確定前チェック E1〜E5（エラー）・W1／W3（警告）は補助関数 `period_close_errors`／`period_close_warnings`。確定のトリガーが E1〜E5 を実行するため、**直接 UPDATE でも迂回できない**。
- ガード（トリガー10本）: 仕訳ヘッダー／明細／期首残高（2表）への書き込み、期の INSERT／日付変更／DELETE／`closed_at` 変更、科目の種別・区分・親の変更、繰越先の変更。値が変わらない UPDATE は通す（`OLD IS DISTINCT FROM NEW`）。
- ロック順: 確定・解除・日付変更は「期の行 → 会社の advisory ロック」、書き込みは「仕訳行 → 期 FOR SHARE」（advisory は取らない）、科目・繰越先は「対象行 → advisory 共有」。確定 RPC は advisory を先取りしない。確定は仕訳行を `FOR UPDATE` しない。明細ガードは `trg_journal_lines_z_closed_guard`（`z_` で既存の親行ロックの後に発火）。BEFORE DELETE は OLD を返し、`TG_OP` で分岐（`coalesce(new, old)` は使わない）。
- 手順0: `closed_at` と開始日・終了日の同時変更は `PERIOD_CLOSED_FIELDS`（E5 迂回の防止）。
- E4 の判定を `lib/financial-statement-calculations.ts` と照合: アプリは「親科目（`parent_id === null`）の `pl_category`／`bs_category` が一致する区分」にだけ金額を載せる（`accounts.filter(... === category)`）。区分が NULL の科目は区分表に載らず脱落する。DB の E4（ASSET/LIABILITY/EQUITY は `bs_category` NULL、REVENUE/EXPENSE は `pl_category` NULL）は同じ条件。補助科目は親から区分を継承するトリガーがあるため、補助科目だけ NULL になることはない。**食い違いなし**。

### `STABLE` の調査結果

- 再現（6パターン、同一トランザクションで作った期に対して）: 単独の `PERFORM period_close_errors(…)`・変数への代入は通る。**式やサブクエリの中（`exists (select … from unnest(period_close_errors(…)))`、関数の引数）から呼ぶと `PERIOD_NOT_FOUND`**。同じブロックが直前に書いた期でも、`create_company` が作った期でも同じ。`VOLATILE` にすると全パターンで通る。
- 原因の推定: `STABLE` 関数は呼び出し元の問い合わせのスナップショットで動くため、同じ PL/pgSQL ブロックが先に書いた行（コマンドカウンタが進む前）が見えない。PostgreSQL の内部動作まで追ったわけではなく、**切り分けの結果（STABLE→VOLATILE で解消）に基づく推定**。
- 実害の確認: ①トップレベルの文として「重なる期をINSERT→同一トランザクションで確定」、②1つの DO ブロック内で「重なる期をINSERT→`close_fiscal_period`」。どちらも STABLE のままで E5 を検出して拒否した（確定のトリガーは文の文脈で呼ぶため）。**現在の呼び出し経路には実害は見つからなかった**が、式の中から使う将来のコードで同じ罠になり得る。
- 対応: `period_close_prev_open`・`period_carry_forward_amount`・`period_close_errors`・`period_close_warnings`・`get_period_close_check` を `VOLATILE` に変更（意図をコメント化）。回帰テスト A12（5本が VOLATILE）・A13（同一ブロック内の式から呼べる）を追加。`STABLE` に戻す変異で落ちる。PostgREST では volatile 関数は POST のみになるが、`supabase.rpc()` は POST なので影響しない（アプリ側での確認は未実施）。
